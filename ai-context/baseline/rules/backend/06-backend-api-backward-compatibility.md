# Правило обратной совместимости backend API

## Статус

Доступно как baseline-правило. Применяется после сопоставления с архитектурой,
стеком и локальными правилами целевого репозитория.

## Цель

Зафиксировать, что публичный backend API в проекте должен оставаться
обратно-совместимым по умолчанию, потому что клиенты и внешние интеграции не
могут обновиться мгновенно после backend-релиза.

## Область применения

Все изменения, которые затрагивают публичный backend-контракт:

- HTTP route и route version в `<admin-api-module>`;
- request/response DTO;
- сериализацию JSON-полей;
- обязательность, типы и семантику входных/выходных параметров;
- use case flow, если он меняет наблюдаемое поведение существующего API.

## Контекст

Клиентские приложения и внешние интеграции могут оставаться на старых версиях
после выкладки backend. Поэтому backend не может рассчитывать, что все
потребители сразу начнут работать по новому контракту.

Следствие: для существующих route и DTO безопасным вариантом по умолчанию
считаются additive-изменения, а не ломающие замены.

## Правило

- При изменении существующего API сначала проверять, можно ли решить задачу
  без breaking change.
- Для уже опубликованных route по умолчанию сохранять обратную совместимость:
  не удалять поля, не переименовывать их, не менять тип и не менять смысл
  существующего поля молча.
- Предпочитать additive-изменения:
  новые optional-поля в response,
  новые optional-параметры в request,
  новые endpoint-ы,
  новые методы в transport/domain-контуре без переписывания старого контракта.
- Если без breaking change обойтись нельзя, поднимать новую версию API в route,
  а не ломать старую. Например, вводить новый versioned endpoint и оставлять
  предыдущий route рабочим до отдельной задачи на вывод из эксплуатации.
- Versioning должен быть явным на уровне route constants и transport-слоя, а
  не прятаться в условной логике controller-а.
- Старую версию API нельзя удалять или менять её поведение без отдельной
  постановки, где явно подтверждён план миграции клиентов.
- Если новая версия API добавлена, AI должен явно зафиксировать это в
  changelog/task-docs, чтобы было видно, какой route считается legacy, а какой
  новым.

## Что запрещено

- молча менять shape существующего JSON response;
- переименовывать или удалять поле в уже используемом API;
- менять тип поля или его семантику в существующем route без version bump;
- делать раньше optional-параметр обязательным в существующем route;
- заменять старый endpoint новой несовместимой логикой под тем же route;
- считать, что mobile-клиенты "просто обновятся", и на этом основании ломать
  текущий контракт.

## Чеклист применения

- проверить, является ли изменение additive относительно текущего API;
- проверить, не ломает ли изменение существующих потребителей;
- если нужен breaking change, создать новую versioned route;
- сохранить старый route и старые DTO рабочими до отдельной миграции;
- зафиксировать в changelog и task-docs, если появилась новая версия API или
  legacy-ветка контракта.
