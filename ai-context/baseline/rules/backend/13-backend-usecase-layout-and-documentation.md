# Оформление и размещение UseCase

## Статус

Доступно как baseline-правило. Применяется после сопоставления с архитектурой,
стеком и локальными правилами целевого репозитория.

## Цель

Сделать каждый domain UseCase понятным с продуктовой точки зрения и убрать
из сценариев ручной инфраструктурный шаблонный код. По структуре feature должно
быть сразу видно, где находится самостоятельный сценарий, а где — общий для
нескольких сценариев вспомогательный компонент.

## Область применения

- Все новые и изменяемые классы `*UseCase` в `<domain-module>`.
- Пакеты `<feature>.usecases` и их вспомогательные классы.
- Вложенные входные и выходные модели UseCase.

## Правила класса UseCase

- В корне пакета `<feature>.usecases` могут находиться только классы,
  представляющие самостоятельные UseCase. Вспомогательные сервисы, политики,
  валидаторы, преобразователи и другие helper-классы нужно размещать в
  `<feature>.usecases.common` либо в более узком подпакете внутри `common`.
- Каждый UseCase обязан иметь JavaDoc класса на принятом в проекте языке. Комментарий
  должен понятным человеку языком объяснять, какой пользовательский или
  системный сценарий реализуется, зачем он нужен продукту и какой значимый
  результат получает пользователь либо система. Недостаточно пересказать имя
  класса или написать «выполняет предметную операцию».
- Класс UseCase обязан наследоваться от `UseCase<Input, Output>` либо от
  подходящего общего/абстрактного UseCase, описанного в
  `08-backend-usecase-standards.md`.
- Зависимости UseCase передаются через конструктор и хранятся в `final` полях.
  Конструктор должен генерироваться Lombok-аннотацией: обычно
  `@RequiredArgsConstructor` или `@AllArgsConstructor`. Ручной конструктор
  допустим только при нетривиальной проверке или преобразовании зависимостей,
  которое невозможно выразить стандартной Lombok-аннотацией; причина должна
  быть явно описана в JavaDoc конструктора.
- Основной метод выполнения обязан переопределять родительский контракт и быть
  помечен `@Override`.
- У метода `execute(...)` не должно быть отдельного JavaDoc: он дублирует
  продуктовое описание класса и контракт родительского UseCase. Смысл
  сценария документируется на классе, а входные и выходные данные — на их
  моделях и полях.
- Все остальные явно объявленные методы UseCase, включая `private` helper-ы,
  обязаны иметь содержательный JavaDoc на принятом в проекте языке. Комментарий должен
  объяснять локальное бизнес-правило, проверяемый инвариант или часть
  оркестрации, а не повторять имя метода.

## Input и Output

- Вложенные `Input`/`InputValues` обязаны реализовывать
  `UseCase.InputValues`, а `Output`/`OutputValues` — `UseCase.OutputValues`,
  если не используется готовый wrapper общего каркаса.
- Для входных и выходных моделей нужно использовать Lombok вместо вручную
  написанных конструкторов, getter-ов, статических фабрик и builder-ов.
- Предпочтительная форма для неизменяемой компактной модели:

```java
@Getter
@AllArgsConstructor(staticName = "of")
public static class OutputValues implements UseCase.OutputValues {
    private final String id;
}
```

- Если требуется пошаговая сборка большого контракта, разрешены `@Builder` или
  `@SuperBuilder` совместно с подходящими constructor/getter-аннотациями.
  Механика builder-а не пишется вручную.
- `@NoArgsConstructor` добавляется только когда он действительно требуется
  сериализации, фреймворку или выбранному Lombok builder-паттерну.
- У класса Input/Output и каждого его поля должен быть JavaDoc на принятом в
  проекте языке,
  раскрывающий назначение данных и важные ограничения.

## Что запрещено

- Размещать в корне `<feature>.usecases` классы, которые сами не являются
  UseCase.
- Создавать UseCase без наследования от общего родительского контракта.
- Оставлять `execute(...)` без `@Override`.
- Добавлять к `execute(...)` JavaDoc, повторяющий JavaDoc класса.
- Оставлять остальные явно объявленные методы без содержательного JavaDoc.
- Писать вручную конструктор UseCase только ради присваивания зависимостей.
- Писать вручную конструкторы, getter-ы, фабрики `of(...)` или builder-классы
  для Input/Output, если эту механику предоставляет Lombok.
- Использовать комментарии вида «выполняет метод», «возвращает результат» или
  пересказ Java-имени без объяснения продуктового смысла.

## Чеклист

- В корне `usecases` остались только `*UseCase`.
- Вспомогательные классы находятся в `usecases.common`.
- JavaDoc класса объясняет продуктовый сценарий на принятом в проекте языке.
- UseCase наследуется от общего родительского класса.
- Конструктор зависимостей генерируется Lombok-аннотацией.
- `execute(...)` имеет `@Override` и не имеет дублирующего JavaDoc.
- Каждый другой явно объявленный метод имеет содержательный JavaDoc.
- Input/Output используют Lombok и не содержат ручной builder-механики.
