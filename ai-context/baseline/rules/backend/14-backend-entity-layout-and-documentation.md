# Оформление и размещение Entity

## Статус

Доступно как baseline-правило. Применяется после сопоставления с архитектурой,
стеком и локальными правилами целевого репозитория.

## Цель

Сделать каждую предметную сущность понятной с точки зрения продукта,
единообразно оформленной в Java-коде и отделённой от вспомогательных типов.
По структуре пакета и комментариям должно быть понятно, что хранится как
самостоятельная сущность, какие данные она представляет и какие бизнес-правила
защищает.

## Область применения

- Все новые и изменяемые `*Entity` в `<domain-module>`.
- Пакеты `<feature>.entity` и `<feature>.entity.common`.
- Вложенные классы, перечисления и поля, объявленные внутри Entity.
- Вспомогательные предметные типы, необходимые Entity.

## Продуктовое описание Entity

- Каждый Entity обязан иметь JavaDoc класса на принятом в проекте языке.
- JavaDoc должен человекопонятно объяснять:
  - какой продуктовый объект или факт представляет Entity;
  - зачем Entity нужен пользователю, администратору или системе;
  - какие ключевые бизнес-решения или процессы зависят от его состояния.
- Недостаточно пересказать имя класса или написать «содержит данные сущности».
- Технические детали хранения допустимы только как дополнение к продуктовому
  смыслу, а не вместо него.

## Структура пакетов

- В корне `<feature>.entity` могут находиться только самостоятельные persisted
  Entity с суффиксом `Entity`.
- Вспомогательные классы, value object-ы, политики, валидаторы, перечисления и
  другие типы, которые сами не являются persisted Entity, размещаются в
  `<feature>.entity.common` либо в более узком подпакете внутри `common`.
- Вложенный вспомогательный класс внутри Entity допустим, если он относится
  только к этой сущности и не используется как самостоятельная модель в других
  сценариях. К нему применяются те же требования по JavaDoc на принятом в проекте языке класса,
  полей и методов.
- Пакет `<feature>.model` в domain-слое запрещён: он смешивает Entity,
  вспомогательные типы и контракты разных назначений. Новый код в `model`
  добавлять нельзя.
- Существующий класс из `model`, который требуется изменить, нужно перенести в
  корректный пакет в рамках отдельной контролируемой задачи с обновлением всех
  импортов и проверкой обратной совместимости. Массовый перенос несвязанных
  legacy-классов «по пути» запрещён.

## Наследование и Lombok

- Каждый persisted Entity обязан наследоваться от подходящего общего
  родительского класса по своей семантике:
  - `BaseEntity<String>` — обычная сущность;
  - `BaseDeleteEntity<String>` — сущность с мягким удалением;
  - `BaseExternalEntity<String>` — сущность с внешними ссылками;
  - `BaseExternalDeleteEntity<String>` — сущность с внешними ссылками и мягким
    удалением;
  - другой согласованный общий Entity-класс, если он точнее описывает lifecycle.
- Entity оформляется базовым набором Lombok-аннотаций:

```java
@Data
@SuperBuilder
@NoArgsConstructor
@EqualsAndHashCode(callSuper = false)
public class ExampleEntity extends BaseEntity<String> {
}
```

- Дополнительные аннотации разрешены, если они действительно нужны
  сериализации, наследованию, framework-контракту или предметному поведению.
- Ручная реализация конструктора, getter-а, setter-а, `equals`, `hashCode`,
  `toString` или builder-а запрещена, если эквивалентный код уже генерируется
  выбранными Lombok-аннотациями.
- Если ручная реализация отличается от стандартной Lombok-семантики и нужна
  бизнес-логике, причина и отличие должны быть явно описаны в JavaDoc метода.

## Поля Entity

- Каждое поле объявляется отдельной декларацией. Объединять несколько полей
  через запятую запрещено.

```java
// запрещено
private String agentIdentityFingerprint, agent, agentVersion;

// правильно
private String agentIdentityFingerprint;
private String agent;
private String agentVersion;
```

- У каждого поля явно указывается модификатор доступа: `private`, `protected`
  или `public`. Package-private поля без модификатора запрещены.
- Каждое поле, включая `static`-поля с предметным или контрактным смыслом,
  обязано иметь отдельную JavaDoc на принятом в проекте языке.
- JavaDoc поля желательно оформлять в одну строку, если бизнес-смысл можно
  передать без потери точности. Краткий комментарий уменьшает размер Entity и
  упрощает чтение её структуры.
- Комментарий должен кратко объяснять конкретный бизнес-смысл значения: что оно
  означает для продукта и, только когда это существенно, какое ограничение или
  решение от него зависит.
- Не нужно добавлять одинаковые для многих полей пояснения о техническом
  источнике значения, например «значение назначает серверная часть» или
  «значение передаёт подтверждённый протокол агента». Источник следует указывать
  только тогда, когда он является значимым бизнес-ограничением конкретного поля.
- Комментарии вида «значение поля `name`», «хранит строку» или простой пересказ
  Java-имени не считаются документацией.
- Если поле хранит идентификатор другой сущности, в JavaDoc нужно явно назвать
  целевую сущность и объяснить смысл связи. Например: «Идентификатор
  `ResourceGroupEntity`, определяющей обязательную группу сервера».
- Для коллекции идентификаторов нужно описать целевую Entity, смысл набора,
  допустимость пустого значения и значимость порядка, если порядок используется.

Предпочтительный формат:

```java
/** Версия агента, сформировавшего технический снимок сервера. */
private String collectorVersion;
```

Избыточный формат без дополнительного бизнес-смысла:

```java
/**
 * Версия агента, сформировавшего технический снимок сервера.
 * Значение назначает серверная часть либо подтверждённый протокол агента.
 */
private String collectorVersion;
```

## Методы Entity и границы чистой архитектуры

- Каждый явно объявленный метод Entity обязан иметь содержательную JavaDoc на
  принятом в проекте языке. Исключение — методы, полностью генерируемые Lombok и не
  объявленные в исходном коде.
- JavaDoc метода должна объяснять бизнес-действие, проверяемые инварианты,
  изменение состояния и значимые внутренние последствия.
- Методы Entity могут:
  - проверять и защищать собственные инварианты;
  - выполнять переходы собственного состояния;
  - рассчитывать результат на основании собственного состояния;
  - нормализовать входное значение только в рамках локального бизнес-правила
    этой сущности.
- Entity не должна реализовывать UseCase. Внутри Entity запрещены оркестрация
  repository/port-ов, проверки прав текущего пользователя, вызовы внешних
  сервисов, transport/persistence DTO и координация нескольких агрегатов.
- Если метод представляет самостоятельный пользовательский или системный
  сценарий, он должен быть вынесен в `<feature>.usecases`.
- Переиспользуемые stateless helper-ы и политики, не зависящие от состояния
  конкретного экземпляра Entity, нужно выносить в `entity.common` либо в
  подходящий общий предметный пакет.

## Вложенные классы и enum

- Вложенный класс внутри Entity обязан иметь JavaDoc на принятом в проекте языке класса.
- Каждое поле и каждый явно объявленный метод вложенного класса документируются
  по тем же правилам, что поля и методы Entity.
- Каждый enum обязан иметь JavaDoc на принятом в проекте языке, объясняющую бизнес-смысл набора
  значений.
- У каждой enum-константы должна быть отдельная JavaDoc на принятом в проекте
  языке с объяснением,
  что это состояние или тип означает для продукта и поведения системы.
- Enum, описывающий разновидность объекта или операции, рекомендуется называть
  с суффиксом `Type`.
- Enum, описывающий состояние жизненного цикла или результата, рекомендуется
  называть с суффиксом `Status`.
- Нейтральное имя без `Type`/`Status` допустимо, если перечисление выражает не
  тип и не состояние, а самостоятельное предметное понятие.

## Что запрещено

- Создавать Entity без продуктовой JavaDoc на принятом в проекте языке.
- Размещать non-Entity классы в корне `<feature>.entity`.
- Создавать или расширять domain-пакет `<feature>.model`.
- Создавать persisted Entity без наследования от подходящего общего Entity.
- Объявлять несколько полей одной декларацией через запятую.
- Оставлять поле без явного модификатора доступа.
- Оставлять поле, вложенный класс, enum или enum-константу без содержательной
  JavaDoc на принятом в проекте языке.
- Скрывать смысл ссылки на другую Entity за общим комментарием «идентификатор».
- Вручную дублировать код, который генерируют Lombok-аннотации Entity.
- Помещать в Entity логику UseCase, инфраструктурные вызовы или координацию
  нескольких агрегатов.

## Чеклист

- В корне `entity` находятся только persisted `*Entity`.
- Вспомогательные типы и enum находятся в `entity.common` или его подпакетах.
- Пакет `model` не создаётся и не расширяется.
- JavaDoc класса объясняет продуктовый смысл Entity на принятом в проекте языке.
- Выбран корректный родитель `BaseEntity`, `BaseDeleteEntity` или аналог.
- Присутствуют `@Data`, `@SuperBuilder`, `@NoArgsConstructor` и
  `@EqualsAndHashCode(callSuper = false)`.
- Lombok-механика не продублирована вручную.
- Каждое поле объявлено отдельно и имеет явный модификатор доступа.
- Каждое поле имеет отдельную, предпочтительно однострочную, продуктовую
  JavaDoc на принятом в проекте языке без шаблонных технических пояснений.
- Для полей-ссылок названа целевая Entity и объяснён смысл связи.
- Все явно объявленные методы документированы и не реализуют UseCase.
- Вложенные классы, enum и enum-константы полностью документированы.
- Для enum по возможности выбрано имя с суффиксом `Type` или `Status`.
