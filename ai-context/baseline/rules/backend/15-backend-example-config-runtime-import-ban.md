# Запрет runtime-импорта example-конфигураций backend

## Статус

Доступно как baseline-правило. Применяется после сопоставления с архитектурой,
стеком и локальными правилами целевого репозитория.

## Цель

Не допустить запуска backend на демонстрационных или неполных настройках из
example-файлов. Example-файл показывает формат конфигурации, но не является
источником runtime-настроек приложения.

## Область применения

Все YAML-конфигурации Spring Boot в `<backend-root>`, включая
`application.yml`, профильные `application-*.yml`, bootstrap-конфигурацию,
тестовые runtime-конфиги и скрипты подготовки окружения.

## Правило

- Файлы с маркером `example` в имени являются только шаблонами и документацией.
- `application.yml` и каждый профильный runtime YAML должны самостоятельно
  содержать полный контракт настроек, необходимый соответствующему окружению.
- Значения, зависящие от окружения, передаются в runtime YAML через environment
  placeholders или штатное хранилище конфигурации и секретов.
- Локальный `application.yml` может содержать значения, необходимые для
  запуска разработчиком, но должен игнорироваться Git. В Git фиксируются только
  example-шаблон, имена параметров и безопасные значения по умолчанию.
- Добавление или изменение runtime-параметра должно синхронно обновлять
  `application.yml` и соответствующий example-шаблон, но эти файлы остаются
  независимыми и не импортируют друг друга.
- При ревью необходимо проверять не только `spring.config.import`, но и другие
  способы runtime-загрузки example-файла: `spring.config.additional-location`,
  `spring.config.location`, `@PropertySource`, программную загрузку ресурсов и
  копирование example-файла поверх рабочего конфига в startup-скрипте.

## Что запрещено

- импортировать `application.example.yml`, `application.example.yaml` или любой
  другой `*.example.yml` / `*.example.yaml` в runtime-конфигурацию;
- использовать конструкцию:

  ```yaml
  spring:
    config:
      import: classpath:application.example.yml
  ```

- подключать example-файл условно через Spring profile или переменную
  окружения;
- загружать example-файл из Java-кода как источник properties;
- копировать example-файл в `application.yml` автоматически перед каждым
  запуском;
- считать успешный старт Spring context доказательством корректной
  конфигурации, если context получил настройки из example-файла.

## Допустимый вариант

Рабочий YAML явно объявляет runtime-контракт. Значение может быть задано прямо
в локальном игнорируемом файле или получено из окружения:

```yaml
application:
  authorization:
    auth-service:
      url: ${AUTH_SERVICE_URL:http://auth-service}
      service-account-token: ${AUTH_SERVICE_TOKEN:}
```

`application.example.yml` может содержать тот же набор ключей как справочный
шаблон, но Spring Boot не должен читать его при запуске.

## Чеклист применения

- проверить все `application*.yml` и `application*.yaml` на ссылки на файлы с
  `example` в имени;
- проверить Java-код, launch/build/startup scripts и environment-настройки на
  альтернативную загрузку example-файлов;
- убедиться, что `application.yml` содержит полный runtime-контракт напрямую;
- убедиться, что локальный `application.yml` с действующими значениями
  игнорируется Git;
- убедиться, что обязательные environment placeholders перечислены в
  `.env.example`, а действующие секреты в нём отсутствуют;
- запустить YAML parsing, backend-тесты и smoke-start без runtime-доступа к
  example-файлам;
- считать правило нарушенным при любой runtime-зависимости рабочего конфига от
  example-файла, даже если приложение успешно запускается.
