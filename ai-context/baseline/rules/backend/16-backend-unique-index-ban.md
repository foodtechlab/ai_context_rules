# Запрет unique-индексов в backend

## Статус

Доступно как опциональный baseline-профиль. Становится обязательным только если
запрет explicit unique-индексов принят в локальных правилах репозитория.

## Цель

Не связывать бизнес-правила уникальности с explicit unique-индексами базы
данных и не допускать падения backend из-за попытки автоматически создать или
изменить такой индекс.

## Область применения

Правило действует для всего `<backend-root>`, включая:

- Mongo documents, repositories и конфигурацию Spring Data;
- ORM-аннотации и persistence-модели других хранилищ;
- программное создание индексов;
- YAML, JSON, JavaScript и другие схемы или init-файлы базы данных;
- backend-тесты, fixtures, документацию и task details, которые задают либо
  требуют explicit unique-индекс.

## Жесткое правило

В backend запрещено объявлять explicit unique-индексы. В частности, запрещены:

```java
@Indexed(unique = true)
@CompoundIndex(def = "{'field': 1}", unique = true)
@Column(unique = true)
@Table(uniqueConstraints = ...)
new Index(...).unique()
```

Также запрещены эквивалентные декларации в любом регистре и формате, например:

```text
unique=true
unique: true
unique(true)
{ unique: true }
```

Нельзя обходить правило вынесением unique-индекса из annotation в startup
runner, Mongo shell script, migration, инфраструктурный init-файл или ручную
инструкцию для окружения.

Системный индекс MongoDB по `_id`, который само хранилище создает для каждого
document, не является нарушением: backend не объявляет для него
`unique = true` самостоятельно.

Обычные неуникальные индексы разрешены, если они обоснованы профилем запросов и
соответствуют правилам Mongo persistence и index compatibility. Для MongoDB они
должны объявляться только через `@CompoundIndex`/`@CompoundIndexes` согласно
`17-backend-mongo-index-annotation-standard.md`; `@Indexed` запрещён независимо
от значения `unique`.

## Как обеспечивать продуктовую уникальность

Запрет индекса не отменяет бизнес-инвариант. Если значение должно быть
уникальным, это явно реализуется в domain/use case и persistence-контракте:

- нормализовать и валидировать бизнес-ключ до сохранения;
- перед созданием или изменением проверять конфликт через repository port;
- возвращать предметную conflict-ошибку, а не инфраструктурную ошибку Mongo;
- для конкурентных запросов использовать согласованный атомарный протокол,
  например детерминированный `_id`, single-document compare-and-set либо иной
  механизм сериализации, не создающий explicit unique-индекс;
- покрывать обычный конфликт и конкурентный сценарий тестами.

Обычная последовательность `exists` → `save` сама по себе не гарантирует
уникальность при гонке. Нельзя выдавать такую проверку за полноценную защиту
конкурентного инварианта.

## Исправление найденного нарушения

При обнаружении `unique = true` или эквивалентной декларации нужно:

1. Удалить unique-опцию из production-кода.
2. Удалить или переписать тесты, которые требуют unique-индекс.
3. Сохранить продуктовую проверку конфликта и при необходимости сделать ее
   безопасной для конкурентных запросов без explicit unique-индекса.
4. Проверить весь backend поиском по всем поддерживаемым формам записи.

## Изменение существующей схемы

Способ удаления существующего unique-индекса зависит от стадии и окружения:

- в disposable development-базе допустимо пересоздать локальное состояние;
- в shared, staging или production-среде изменение выполняется управляемой,
  проверяемой и обратимой миграцией по принятому в проекте процессу;
- startup beans и неявное удаление индексов при запуске не заменяют миграцию;
- перед удалением нужно проверить влияние на конкурентную уникальность,
  данные, rollback и совместимость версий приложения.

## Проверка агентом

После изменения persistence-кода обязательно выполнить поиск как минимум по
следующим формам:

```bash
rg -n -i \
  'unique\s*=\s*true|unique\s*:\s*true|\.unique\s*\(\s*\)|\.unique\s*\(\s*true\s*\)|uniqueConstraints' \
  <backend-root> \
  --glob '!**/target/**'
```

Результат допустим только в тесте архитектурного запрета или документации,
которая показывает запрещенный пример. Production-код, persistence-тесты и
runtime-конфигурация не должны содержать такие декларации.

## Чеклист ревью

- Во всем backend отсутствуют explicit unique-индексы.
- Запрет не обойден через annotation другого persistence framework.
- Запрет не обойден через программное создание или init-script.
- Продуктовый конфликт обрабатывается на уровне domain/use case.
- Конкурентный сценарий не полагается только на `exists` перед `save`.
- Тесты не требуют `unique = true` и проверяют предметное поведение.
- Для существующих shared/production данных подготовлена безопасная миграция
  либо доказано, что физического индекса ещё нет.
- Выполнены релевантные тесты и `git diff --check`.
