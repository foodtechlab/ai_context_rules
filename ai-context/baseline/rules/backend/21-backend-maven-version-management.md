# Управление версиями Maven-зависимостей и плагинов

## Статус

Доступно как baseline-правило. Применяется после сопоставления с архитектурой,
стеком и локальными правилами целевого репозитория.

## Цель

Использовать единый источник версий Maven, не вводить скрытые переопределения
и несогласованные обновления при рефакторинге.

## Область применения

Новые и изменяемые объявления зависимостей, плагинов и их версий во всех
`<backend-root>/**/pom.xml`. Правило само по себе не разрешает обновлять
библиотеки или массово переписывать несвязанные существующие POM.

## Правило

1. Сначала проверить parent, импортированные BOM, `dependencyManagement`,
   `pluginManagement` и доступные version properties. Не выбирать версию по
   памяти или только по локальному Maven cache.
2. Если версия зависимости уже управляется parent/BOM/root POM, не указывать
   `<version>` повторно в потребляющем модуле. Это относится и к test dependencies.
3. Если версия плагина уже управляется унаследованным `pluginManagement`,
   не дублировать её. Если parent предоставляет только property, явно связать
   plugin с ней: например, `<version>${build.surefire.version}</version>`.
   Само наличие property не означает, что Maven применяет её к plugin.
4. Если подходящего управления версией нет, завести именованную property
   в корневом backend POM и ссылаться на неё через `${...}`. Для общих
   зависимостей использовать root `dependencyManagement`, для общих плагинов —
   root `pluginManagement`; подключать их в необходимых модулях без копирования версий.
5. Не записывать числовую/строковую версию напрямую в `<dependency><version>`
   или `<plugin><version>`, включая management-секции. Значения собственных
   версий хранятся в properties; унаследованные значения повторно не объявлять.
6. Не переопределять property parent локально только ради сохранения случайно
   выбранной Maven версии. Необходимое отступление согласовать с пользователем,
   обосновать в задаче и проверить; оформление через property само по себе
   не делает произвольную смену версии допустимой.
7. Перед изменением сравнить effective версии до/после. Подстановка `${...}`
   может реально сменить версию инструмента, а не только оформление XML.
   После изменения test engine/provider/plugin запустить backend-тесты и
   сверить обнаружение по модулям; успешная сборка без ожидаемых тестов не принимается.

## Границы и исключения

- Версия внешнего `<parent>` может оставаться литералом: это координата для
  загрузки самого parent, а не управляемая им dependency/plugin. Не заменять
  её свойством, доступным лишь после загрузки parent.
- Существующие project/module version conventions (`${revision}` и аналоги)
  сохраняются; это правило не вводит новую схему версионирования проекта.
- Найденный legacy hardcode вне текущей задачи зафиксировать для отдельного
  изменения. Не совмещать его исправление с несвязанной бизнес-правкой.

## Чеклист применения

- Найден реальный источник версии и проверен effective POM.
- Нет дублирующей версии managed dependency/plugin и нового version hardcode.
- Нет необоснованного переопределения parent properties.
- Реальная смена версии явно описана, выполнены соответствующие проверки.
- При чисто тестовой правке production-зависимости и поведение сохранены.
