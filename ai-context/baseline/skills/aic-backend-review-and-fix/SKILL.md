# Backend Review and Fix

Проверять backend-код по фактическому стеку, архитектуре и правилам текущего
репозитория. Начинать с незакоммиченного diff и исправлять только безопасные
замечания в выбранном scope. Если пользователь явно просит только ревью, не
менять файлы.

## Подготовка

1. Определить корень репозитория и прочитать полностью существующие файлы:
   - `ai-context/parameters/repository-parameters.yaml`;
   - `ai-context/baseline/guides/tasks.md`;
   - `ai-context/baseline/guides/changelog.md`;
   - `ai-context/baseline/rules/backend/README.md`;
   - все применимые Markdown-файлы из `ai-context/baseline/rules/backend/`;
   - `ai-context/rules/backend/README.md` и все Markdown-файлы из
     `ai-context/rules/backend/`, если они существуют.
2. Определить backend-каталоги, модули, язык, build system и тестовые команды
   по структуре репозитория и его документации. Не предполагать конкретный
   framework, package prefix или имя модуля.
3. Сначала применять project-specific правила из `ai-context/rules/backend/`,
   затем совместимые с реальным стеком baseline-правила. При конфликте
   project-specific правило имеет приоритет.
4. Не редактировать `ai-context/baseline/**`. Долгоживущие project-specific
   решения фиксировать в локальном слое `ai-context/rules/`.

## Определение scope

1. Выполнить `git status --short`, получить staged, unstaged, renamed и
   untracked файлы, затем выделить backend-код и связанные runtime/config
   файлы. Исключить generated/build output.
2. Если пользователь явно указал модуль, файлы, задачу или feature-slice,
   использовать этот scope.
3. Иначе при наличии незакоммиченных backend-изменений ревьюить в первую
   очередь их. Соседние файлы читать как контекст, не расширяя изменения без
   необходимости.
4. Если незакоммиченного backend-кода нет и пользователь не задал scope,
   спросить, что проверить. Не запускать полный аудит автоматически.
5. Не изменять unrelated пользовательские изменения и legacy-код вне scope.

## Ревью

Проверить только применимые к обнаруженному стеку аспекты:

- границы модулей, слоев и feature-slice;
- направление зависимостей и отсутствие обхода публичных контрактов;
- повторное использование существующих contracts, ports и adapters вместо
  параллельных реализаций;
- доменные entity, value objects, use cases и их инварианты;
- API DTO, transport boundaries, routes и обратную совместимость;
- persistence documents/models, mappers, queries, indexes и repositories;
- authentication, authorization и границы доверия;
- runtime wiring, configuration, schedulers и внешние интеграции;
- обработку ошибок, наблюдаемость и отсутствие утечек чувствительных данных;
- тесты для измененной бизнес-логики и критичных контрактов;
- требования project-specific и совместимых baseline backend-правил.

Каждый finding привязывать к конкретному правилу и файлу/строке. Не считать
нарушением неприменимое к стеку правило и не переносить доменные требования из
других проектов.

## Исправления

1. Исправлять нарушение сразу, если изменение безопасно, минимально и входит
   в scope.
2. Не делать unrelated refactor и не менять публичные контракты без явной
   необходимости.
3. Перед потенциально breaking-изменением обозначить риск и запросить решение.
4. Если исправление требует продуктового или архитектурного решения, оставить
   finding с файлом/строкой, объяснением и безопасным следующим шагом.
5. Не изменять код в режиме review-only.

## Проверки и завершение

1. После исправлений запустить наиболее узкие релевантные compile, lint и
   test-команды затронутых модулей, а также `git diff --check`. Не подменять
   реальные команды предположениями о build system.
2. Если были file changes, вести задачу, changelog, completion alert и резюме
   для коммита по workflow текущего `ai-context`.
3. В финальном ответе сначала перечислить найденные и исправленные проблемы,
   затем неисправленные findings и результаты проверок.
4. Если изменений нет, явно написать, что коммит не требуется.

## Запрещено

- читать project-specific или применимые baseline backend-правила частично;
- ревьюить весь backend без явного scope при отсутствии dirty backend diff;
- навязывать конкретные framework, library, package prefix, route или
  security contract, которых нет в текущем репозитории;
- исправлять unrelated legacy-код;
- делать рискованные архитектурные или breaking-изменения без согласования;
- удалять или откатывать пользовательские изменения;
- пропускать релевантные проверки или обязательный workflow после file changes.
