# Collect Backend Entities

Анализировать backend текущего репозитория и атомарно обновлять только
`ai-context/apps/backend-entity-map/data/generated.json`.

## Контракты

Перед сбором прочитать полностью:

- `ai-context/baseline/apps/backend-entity-map/schemas/generated.schema.json`;
- `ai-context/baseline/apps/backend-entity-map/README.md`;
- `ai-context/parameters/repository-parameters.yaml`, если файл существует;
- project-specific backend rules и документацию, влияющие на определение
  domain-модели.

`user.json` принадлежит пользователю. Не изменять, форматировать или
пересоздавать его.

## Scope

1. Определить backend roots, модули, языки и domain packages по структуре и
   документации репозитория. Не предполагать Java, конкретный framework или
   соглашение именования.
2. Собрать все типы, которые фактически относятся к domain-модели:
   - `entity` — самостоятельные domain entities и aggregates;
   - `enum` — перечисления, используемые этими сущностями или их вложенными
     значениями;
   - `inner-class` — вложенные/внутренние классы, объявленные внутри backend
     типов и участвующие в модели.
3. Не включать API DTO, persistence documents, controllers, repositories,
   mappers, configuration и utility-классы только из-за похожего имени.
4. Для каждого элемента прочитать исходный файл целиком. Не строить описание
   только по имени файла или результату поиска.

## Сбор данных

- Использовать стабильный id `<kind>:<qualified-name>`; для вложенного типа
  сохранять нативную квалификацию языка, например `Outer$Inner`.
- Записывать repository-relative `sourcePath` и точную строку объявления.
- Сохранять module, qualified name, поля и значения enum.
- Для каждого поля записывать `description`, взятый из документационного или
  обычного комментария, который относится непосредственно к объявлению этого
  поля. Учитывать аннотации между комментарием и объявлением. Удалять только
  синтаксическую разметку комментария, сохраняя его смысл.
- Не подменять комментарий поля документацией getter/setter, конструктора,
  параметра метода или всего класса. Не придумывать описание по имени и типу
  поля. Если относящегося к полю комментария нет, записывать пустую строку.
- Для каждого класса пройти полную доступную цепочку наследования и включить в
  его `fields` также instance-поля всех предков. Искать исходники предков как в
  репозитории, так и в доступных source dependencies; не ограничиваться
  непосредственным родителем. Static- и synthetic-поля не включать.
- Для унаследованного поля ставить `inherited: true` и записывать в
  `declaredIn` qualified name класса, где поле объявлено. Его `description`
  брать из комментария именно в этом классе-предке по тем же правилам, что и
  для собственного поля.
- Разрешать generic-типы предков в контексте конечной сущности: например, поле
  `Id id` из `BaseEntity<Id>` для потомка `User extends BaseEntity<String>`
  записывать с типом `String`.
- Располагать сначала унаследованные поля — от ближайшего предка к корневому,
  затем собственные поля сущности. Если потомок объявляет поле с тем же именем,
  показывать только поле потомка. Если исходники предка недоступны, не
  придумывать его поля и перечислить такой предок в результате как unresolved.
- Брать описание из документации типа. Если документации нет, дать краткое
  проверяемое описание по поведению и пометить `descriptionSource: inferred`.
  Если надежный вывод невозможен, оставить пустое описание и поставить
  `descriptionSource: missing`.
- Создавать relations только при подтвержденной связи: поле/тип, inheritance,
  implementation, containment или явная ссылка по идентификатору.
- Не создавать relation на тип, отсутствующий в `elements`.
- Сортировать элементы детерминированно по `kind`, `qualifiedName`, а связи —
  по `source`, `target`, `kind`, `id`.
- Устанавливать `source.coverage: full` только после обхода всех найденных
  backend roots. Для явно ограниченного пользователем тренировочного scope
  использовать `sample` и назвать ограничение в итоговом ответе.

## Запись и проверка

1. Сначала сформировать новый JSON во временном файле рядом с целевым.
2. Проверить schemaVersion, уникальность ids, допустимые kinds, существование
   endpoints каждой relation и корректность JSON.
3. Если приложение доступно, запустить из корня репозитория:

   ```bash
   AIC_REPO_ROOT="$PWD" node ai-context/baseline/apps/backend-entity-map/scripts/validate-data.mjs
   ```

4. Заменить `generated.json` только после успешной проверки. При ошибке
   сохранить прежний файл и сообщить диагностику.
5. В результате указать backend roots, coverage, количество элементов каждого
   типа, количество связей, inferred/missing descriptions элементов, число
   собственных и унаследованных полей, число полей без комментариев,
   unresolved ancestors и результат валидации.
