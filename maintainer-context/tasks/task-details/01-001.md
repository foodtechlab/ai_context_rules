# Задача [01-001]

## Короткое описание

Создать переносимый code-first движок дизайн-систем и интерактивных прототипов
с рабочим названием `design-system-studio`. Движок должен поставляться как
React-приложение в baseline, запускаться внутри целевого репозитория, показывать
компоненты и экраны во всех состояниях, строить карты экранов через React Flow и
позволять проходить пользовательские сценарии в mock-режиме.

## Цель

Получить общий каркас, с помощью которого команда может проектировать интерфейс
продукта сразу в исполняемом и versioned виде, а затем переносить результаты в
Web, Flutter, Android и iOS через явные платформенные адаптеры.

После установки `ai-context` целевой репозиторий должен иметь возможность:

- создать собственную дизайн-систему поверх baseline runtime;
- описать design tokens, компоненты, состояния, экраны и переходы;
- открыть компоненты и экраны в браузере без запуска основного продукта;
- переключать состояния и размеры viewport;
- собирать карты экранов из нескольких экранов;
- запускать карту как интерактивный mockup и проходить сценарии;
- хранить весь project-specific дизайн локально в репозитории;
- экспортировать платформонезависимую модель и генерировать платформенные
  заготовки через адаптеры;
- устанавливать, обновлять и запускать приложение с помощью repository skill.

## Контекст и архитектурные решения

### Размещение и ownership

- Переносимый runtime и schemas:
  `ai-context/baseline/apps/design-system-studio/`.
- Все файлы baseline runtime/library неизменяемы в целевом репозитории.
- Project-specific tokens, реализации компонентов, layouts, screens, flows,
  mockups и настройки находятся в настраиваемой директории вида
  `<project-path>/design-system/` вне `ai-context/baseline`.
- Baseline-sync может обновлять runtime, но не должен перезаписывать
  project-specific дизайн, реализации и пользовательские данные.
- Приложение относится к AI Context Apps и не входит в runtime основного
  продукта.

### Code-first и переносимость

React используется для редактора, browser preview и reference Web renderer.
React-компоненты сами по себе не считаются переносимым контрактом для Flutter,
Android или iOS. Каноническим source of truth должна быть serializable,
versioned и platform-neutral модель дизайн-системы.

Модель должна описывать:

- tokens: цвета, типографику, spacing, размеры, radius, elevation, motion и
  семантические aliases;
- component definitions: свойства, slots, variants, states, размеры,
  accessibility metadata и поддерживаемые действия;
- component examples: комбинации props и состояний для каталога;
- screens: дерево элементов, bindings, layout constraints, viewport presets и
  screen states;
- screen maps: узлы экранов, координаты, группы, переходы и сценарии;
- prototypes: события, guards, actions, navigation, mock state и test fixtures;
- export metadata: стабильные ids, platform names и настройки adapters.

Persisted-формат должен иметь `schemaVersion: 1`, JSON Schema и детерминированную
сериализацию. До первого стабильного релиза структура v1 изменяется напрямую,
без migration layer. Платформенные adapters читают каноническую модель и
генерируют код или заготовки; они не изменяют source data.

## Функциональные области

### 1. Design tokens

- Просмотр и редактирование token groups и semantic aliases.
- Light/dark и дополнительные themes без копирования всей системы.
- Предпросмотр контрастности, типографики, spacing и основных foundations.
- Проверка ссылок, циклов и отсутствующих токенов.

### 2. Каталог компонентов

- Компоненты показываются во всех объявленных variants и states.
- Минимальные состояния: default, hover, focus, active, disabled, loading,
  error и empty, если они применимы к компоненту.
- Для каждого примера можно менять props, theme и viewport.
- В каталоге видны accessibility metadata и platform support.
- Project-specific реализации не записываются в baseline.

### 3. Экраны и responsive states

- Экран собирается из зарегистрированных компонентов.
- Один экран может иметь несколько состояний: default, loading, empty, error,
  success и domain-specific states.
- Экран можно открыть в стандартных и произвольных разрешениях.
- Необходимо поддержать как минимум phone, tablet и desktop presets, не
  привязывая модель к конкретной платформе.
- Состояние preview должно воспроизводиться по URL или стабильному id.

### 4. Карты экранов

- React Flow используется для размещения экранов и отображения переходов.
- Узел карты показывает миниатюру, название, state и viewport экрана.
- Поддерживаются группы/flows, подписи переходов, начальная точка и несколько
  сценариев на одной карте.
- Layout карты сохраняется локально и переживает перезагрузку приложения.
- Карта и отдельный экран имеют стабильные ids, пригодные для ссылок и diff.

### 5. Mockup/prototype mode

- Карту можно запустить с выбранной стартовой точки.
- Клики и другие объявленные события изменяют mock state или выполняют переход.
- Можно вернуться назад, перезапустить сценарий и выбрать fixture.
- Все переходы выполняются без backend основного продукта.
- Ошибки сценария показываются явно; запрещено выполнять произвольный
  непроверенный код из JSON через `eval` или эквиваленты.

### 6. Persistence и локальная работа

- Все изменения сохраняются в `<project-path>/design-system/`.
- После перезагрузки браузера и перезапуска сервера tokens, компоненты, экраны,
  карты, координаты, mocks и prototype state definitions восстанавливаются.
- Запись файлов выполняется атомарно и только внутри разрешенной app data zone.
- Должны быть import/export и понятная диагностика schema errors.
- Baseline update не удаляет и не форматирует repo-local данные без запроса.

### 7. Platform adapters

- Определить стабильный adapter API и capability matrix.
- В MVP реализовать reference Web/React adapter.
- Для Flutter, Android/Compose и iOS/SwiftUI подготовить контракты adapters и
  минимальные proof-of-concept exports, не обещая автоматический production
  parity без платформенной доработки.
- Генерируемые файлы должны отделяться от handwritten code и поддерживать
  повторную генерацию без потери ручных изменений.

### 8. Skill и перенос в целевой репозиторий

- Добавить repository skill `aic-design-system-studio` с префиксом `AIC: ` в
  пользовательском названии.
- Skill должен уметь bootstrap-ить отсутствующие repo-local файлы, проверять
  зависимости, запускать studio и объяснять, какие данные принадлежат baseline,
  а какие проекту.
- Повторный запуск обновляет baseline runtime штатным механизмом и сохраняет
  project-specific дизайн.
- Добавить VS Code launch/task или задокументированную эквивалентную команду.

## Критерии готовности

- Приложение находится в `ai-context/baseline/apps/design-system-studio/`,
  устанавливается и запускается из корня целевого репозитория.
- Repo-local дизайн и реализации хранятся только в настраиваемой директории
  `<project-path>/design-system/` и переживают reload, restart и baseline
  update.
- Design tokens имеют themes, aliases, schema validation и preview.
- Каталог показывает компоненты и их заявленные variants/states.
- Экраны открываются минимум в phone, tablet и desktop viewport и поддерживают
  несколько UI states.
- React Flow карта состоит из нескольких экранов, сохраняет layout и показывает
  переходы.
- Mock mode позволяет пройти минимум один многоэкранный сценарий без backend.
- Есть стабильные ids/deep links для component example, screen state, map и
  prototype scenario.
- Reference Web adapter создает повторяемый результат из канонической модели.
- Контракты Flutter, Compose и SwiftUI adapters документированы и проверены
  минимальными examples.
- Skill устанавливает/bootstrap-ит и запускает studio без перезаписи
  project-specific данных.
- Production build, schema validation, automated tests и browser smoke test
  проходят локально.
- Документация объясняет ownership, запуск, обновление, расширение renderer и
  ограничения cross-platform переноса.

## Нефункциональные требования

- TypeScript strict mode для нового приложения.
- Детерминированные persisted-файлы и человекочитаемые diff.
- Никакого `eval` для пользовательских сценариев и данных.
- Ошибка одного preview не должна ломать весь editor.
- Editor должен оставаться работоспособным без внешнего облачного сервиса.
- Архитектура не должна требовать включения studio в production bundle продукта.
- Любое действие, изменяющее файл, должно явно показывать success/error state.
- Интерфейс должен отличать baseline/reference content от project-owned content.

## Вне scope первой версии

- Полная автоматическая генерация production-ready интерфейсов с одинаковым
  поведением на всех платформах.
- Замена Figma или платформенных accessibility/performance проверок.
- Совместное редактирование в реальном времени и облачный backend.
- Выполнение произвольного product code без sandbox/явной регистрации.
- Автоматический merge с handwritten platform code без generated boundaries.

## Риски и открытые решения

- Слишком выразительная DSL может стать вторым UI framework; spike должен
  определить минимальный контракт и extension points.
- Произвольные React-компоненты усложняют sandbox, сериализацию и переносимость;
  требуется registry с явными props/actions и изолированный preview.
- Cross-platform fidelity ограничена различиями layout, navigation,
  accessibility и native controls; capability matrix должна показывать gaps.
- Большие карты и множество live previews могут быть тяжелыми; нужны lazy
  rendering, thumbnails и virtualization.
- До реализации нужно решить, какие изменения выполняются через UI, а какие
  остаются code-first файлами с preview в studio.
